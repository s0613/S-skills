## 생성 품질

### 기능으로 잘못 잡은 것
없음(발견 못 함). 55행 모두 실제 라우트(`page.tsx`/`route.ts`)에서 출발했고, 유틸리티·설정 파일을 기능으로 잡은 사례는 스스로 점검한 한도 내에서 없었다.

### 빠뜨린 기능 — **가장 중요한 발견**
버그 대조(아래) 중 `c8e87f2`(알림 벨 되살리기)를 추적하다 `src/lib/notify/`(팬아웃 인프라, `buyer-notify.ts` + 자체 테스트)와 `src/components/layout/notification-bell.tsx`(전역 셸에 박힌 벨 위젯)를 발견했다. 이 둘은:
- 어떤 라우트의 `page.tsx`에도 속하지 않는다 — 벨은 `buyer-shell.tsx`(레이아웃)에 박혀 전 화면에 떠 있고, 팬아웃은 여러 기능의 서버 액션에서 옆으로 호출된다.
- 그래서 "라우트·엔트리포인트에서 출발한다"는 생성 규칙을 있는 그대로 따르면 **구조적으로 지도에서 빠진다.** 미매핑 후보로도 못 걸렀다 — 애초에 페이지가 아니라서 탐색 대상에 안 걸린다.
- F53(Gmail 연동)·F54(웹푸시 인프라)는 같은 "레이아웃 전 구간에 걸친 인프라"인데 우연히 `src/app/api/integrations/gmail`, `src/app/api/push`라는 자기 라우트가 있어서 행으로 잡혔다. `src/lib/notify/`는 자기 라우트가 없어서 못 잡혔다 — **규칙이 "이 기능에 전용 라우트가 있는가"에 의존한다는 뜻이고, 그 조건은 문서화돼 있지 않다.**

### `## 미매핑`에 들어간 것
6개 항목(정적 법적 페이지 2개, 프리뷰 도구 1개, SEO 인프라 묶음 1개, 크론 대상 불확실 1개, 목적 불명 보조 API 묶음 1개) + 1개는 지도 생성과 무관한 발견(architecture.md/STATUS.md가 서술하는 `/api/chat` → hybrid 검색 엔진 → 4agent 파이프라인 및 `/for-suppliers` 랜딩이 **코드에 존재하지 않음** — 두 문서가 최근 리팩터를 반영하지 못한 낡은 상태로 보인다).

타당했나: 대체로 타당하다고 본다 — 이 항목들은 사용자 대면 "기능"이라기보다 콘텐츠·인프라·불확실한 소유 관계였다. 다만 위 "빠뜨린 기능"(`src/lib/notify/`)은 애초에 미매핑 후보로도 떠오르지 않았다는 게 문제다 — `## 미매핑`은 "페이지인데 확신이 안 서는 것"만 잡아내고, "페이지가 아닌데 실제로 기능인 것"은 설계상 사각지대다.

### 굵기(granularity) 판단 — 규칙에 없는 것
공급사 ERP(F15-F32, 17행)와 관리자(F33-F52, 20행)를 각각 "라우트 1개 = 행 1개"로 잘게 쪼갰다. 근거: 각 라우트가 자기 전용 `actions.ts`를 갖고 있어(코드로 확인) 서로 독립적으로 고장 날 수 있다고 판단했다. 하지만 이건 s-skills(스킬 1개 = 기능 1개)에서 가져온 습관적 판단이지, `feature-map.md`나 `docs-organize` SKILL.md 어디에도 "라우트 1개를 기능 1개로 볼지, 관련 라우트 묶음을 기능 1개로 볼지"에 대한 기준이 없다. 만약 반대로 판단했다면(예: "공급사 ERP" 전체를 행 1개로) 지도는 17+20행이 아니라 2행이 됐을 것이고, 그 2행의 `핵심 파일`은 "최대 3개" 규칙과 정면으로 충돌했을 것이다(디렉토리가 17개인데 3개만 적을 수 없다). **결국 "최대 3개" 제약이 은연중에 굵기를 강제하고 있다** — 이 프로젝트 규모(128 라우트)에서는 세분화 외에 다른 선택지가 사실상 없었다.

## 판정

이 지도는 "라우트 기반 CRUD 기능"에는 꽤 쓸모 있다 — 3건 중 2건(자기 디렉토리 안에서 끝나는 흔한 버그)에서 진입점과 파급 예측이 정확히 맞아떨어졌고, 55행 모두 STALE·DANGLING 없이 코드와 일치한다. 하지만 딱 그만큼만 쓸모 있다: 페이지에 묶이지 않는 횡단 관심사(알림 팬아웃, 레이아웃에 박힌 위젯, 공유 lib를 통한 암묵적 의존)는 생성 규칙("라우트·엔트리포인트에서 출발")이 구조적으로 놓친다. 세 기계 검사도 전부 1차 시도에서 실패했다는 점(경로 추측 오류, 표↔흐름도 손 동기화 누락)은, 사람이 수작업으로 표를 채우는 한 이 형식이 스스로 검증 없이는 정확할 수 없다는 뜻이기도 하다 — drift 검사가 왜 "기계 검증"으로 존재해야 하는지에 대한 실증이기도 하다. "고장났을 때 이걸 보고 어디를 고칠지 알 수 있나"라는 질문에 대한 답은 **"라우트 안에서 끝나는 버그라면 그렇다, 라우트 경계를 넘나드는 버그라면 아니다"** — 후자가 이번 3건 중 1건이었고, 표본이 작아 일반화하긴 이르지만 무시할 빈도는 아니다.

## 다음 개선 후보 (우선순위 순)

1. **횡단 인프라(레이아웃/공유 lib) 포착 규칙 부재** — `docs-organize` FEATURE-MAP 생성 규칙이 "라우트에서 출발"만 말하고, 라우트가 없는 전역 위젯·팬아웃 lib(`src/lib/notify/`류)를 잡아낼 방법이 없다. `## 미매핑`이 "페이지인데 확신 안 서는 것"만 겨냥해서, "페이지가 아닌 기능"은 후보로도 안 뜬다. 규칙에 "레이아웃/전역 컴포넌트에서 호출되는 공유 lib 중 자체 테스트가 있는 것도 후보로 스캔" 같은 보완이 필요해 보인다.
2. **표↔mermaid 손동기화의 오류율** — 이번에 표와 흐름도를 같은 세션에서 직접 작성했는데도 1개 엣지가 빠졌다. 55행 규모에서는 실수가 나온다는 뜻 — `## 갱신 시점`에 "표를 고치면 흐름도는 (스크립트 없이) 사람이 다시 옮긴다"고만 되어 있는데, 이 정도 규모부터는 흐름도를 표에서 기계적으로 뽑아주는 한 줄짜리 변환(awk/스크립트)이 있으면 이런 드리프트 자체가 안 생긴다.
3. **굵기 기준 부재** — "라우트 1개 = 행 1개"와 "관련 라우트 묶음 = 행 1개" 중 무엇을 고를지 기준이 없다. 이번엔 "핵심 파일 최대 3개" 제약이 사실상 세분화를 강제했는데, 이게 의도된 설계인지 우연인지 규칙 문서에 안 쓰여 있다.
4. **경로 정확성 검증 습관** — 초안 3곳에서 실제 테스트 파일 위치를 얕은 디렉토리로 추측했다가 STALE에 걸렸다. `find`로 먼저 확인하지 않고 패턴만으로 경로를 채우면 이 정도 규모에서는 매번 몇 개씩 틀린다 — docs-organize 지시문에 "경로는 쓰기 전에 존재를 확인한다" 같은 명시적 문구를 추가할 여지가 있다.
