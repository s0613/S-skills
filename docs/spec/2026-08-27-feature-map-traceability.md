# 스펙 — 기능 지도와 추적성 (Feature Map & Traceability)

> 작성: 2026-08-27 · 승인: 사용자 (안 2 — 단일 지도 + 추적성 표, drift 게이트를 세트로)

## 왜 (배경)

**진단.** 하네스는 기능 하나를 깊게 파는 힘(수직)은 갖췄지만, 기능들이 서로 엮이는 면(수평)이 비어 있다.

- 이미 있는 것: sj-spec이 에러 케이스·엣지 케이스·수용 기준·상태 변화를 강제하고, pm-brief는 완료 조건을 기계 검증 가능한 형태로 요구하며, sj-qa가 이를 1:1 대조해 독립 판정한다.
- 없는 것 (2026-08-27 grep 확인):
  - `"영향 범위"` — 전 스킬·전 플레이북 통틀어 sj-investigate 1건, 그것도 **버그가 터진 뒤 사후 조사**.
  - `"의존 관계"` — sj-tech-lead 1건, 서브에이전트 **호출 순서** 의미이지 기능 간 의존이 아님.
  - `"추적성/traceability"` — **0건**. 수용 기준이 파일·함수·테스트에 연결되어 있지 않다.
  - 기능 단위 흐름도 — mermaid를 쓰는 스킬은 obsidian-writer(문서 정리용) 하나뿐.
- **결과:** sj-qa가 FAIL을 내도 판정문에 *어디를 고쳐야 하는지*가 없다. 사람도 AI도 매번 코드베이스를 재탐색한다. `spec-{feature}.md`는 파편으로만 쌓이고 "이 프로젝트의 기능 전체와 그 연결"을 담은 단일 사실이 없다.

**외부 확인.** SDD 진영의 공통 지적 — AI 에이전트가 생성한 코드 상당수가 문서화된 요구사항으로 역추적되지 않고, 명세되지 않은 기능의 테스트가 존재하는 반면 명시적으로 스코프한 기능은 누락된다.

**경쟁 하네스 조사 (2026-08-27).**

|---|---|---|

**결론 두 가지.**
1. 넷 모두 "이 변경 하나"만 본다 — **기능 A를 고치면 B가 깨진다**를 구현 전에 따지는 단계는 어디에도 없다. 우리가 메우려는 자리는 실제로 빈 자리다.
2. 그러나 drift 감지는 셋이 갖고 있고 우리는 없다. **지도는 drift 게이트와 반드시 세트여야 한다** — 틀린 지도는 지도 없느니만 못하다.

## 무엇을 (설계)

### 1. 산출물 — `docs/FEATURE-MAP.md` (대상 프로젝트 repo, 정본)

```markdown
# Feature Map
> 이 프로젝트의 기능 목록과 서로의 연결. 코드와 같은 커밋에서 갱신된다.
> 갱신 규칙: s-skills `skills/_conventions/feature-map.md`

## 흐름
```mermaid
flowchart LR
  F01[바이어 로그인] --> F02[견적 요청]
  F02 --> F03[관리자 인박스]
```

## 기능
| ID | 기능 | 진입점 | 핵심 파일 | 테스트 | 의존 |
|----|------|--------|-----------|--------|------|
| F01 | 바이어 로그인 | `src/app/(buyer)/login/page.tsx` | `src/lib/auth/` | `src/lib/auth/__tests__/login.test.ts` | — |
| F02 | 견적 요청 | `src/app/api/inquiries/route.ts` | `src/lib/sales/sales-inquiry.ts` | `src/lib/sales/sales-agent-tools.test.ts` | F01 |

## 미매핑
- (코드에는 있으나 기능으로 등록되지 않은 것)
```

**칸 규칙**
- `ID` — `F{2자리}` 프로젝트별 순번. **삭제된 기능의 ID는 재사용 금지**(과거 판정문·커밋의 참조가 깨지면 추적성이 무너진다). 폐기는 행을 지우지 말고 기능명에 `(폐기)` 표기.
- `진입점` — "여기부터 읽어라". 라우트·핸들러·페이지 등 흐름이 시작되는 파일 1개.
- `핵심 파일` — "여기 안에서 고쳐라". 파일 또는 디렉토리, 최대 3개. **여러 개는 공백 또는 쉼표로 구분**하고 디렉토리는 끝에 `/`를 붙인다 (drift 검사가 이 구분자로 쪼갠다).
- `테스트` — 이 기능의 회귀를 잡는 테스트 경로. 없으면 `없음`(빈칸 금지 — 없다는 사실이 신호다).
- `의존` — 이 기능이 **의존하는** 기능 ID 목록. 역방향(나를 의존하는 기능)은 표에서 파생 계산하므로 적지 않는다.
- `상태` 칸 없음 — PROJECT.md가 이미 진행 상태를 갖는다. 중복 금지.

**표가 정본, mermaid는 파생.** 의존 칸을 고치면 흐름도 블록을 표에서 다시 생성한다. 둘을 각각 손대는 순간 그 자체가 drift 원인이 된다.

### 2. 컨벤션 — `skills/_conventions/feature-map.md` (규칙 정본)

위 칸 규칙 + 갱신 시점 + drift 검사 + 폴백을 규정한다. `_conventions/README.md` 규칙 표에 행을 추가한다.

**drift 검사 (기계 검증)**
```bash
# 표의 경로가 실존하는가 — 실존하지 않으면 지도가 낡음
awk -F'|' '/^\| *F[0-9]/ {print $4 $5 $6}' docs/FEATURE-MAP.md \
  | tr -d '`' | tr ' ,' '\n\n' | grep -v '^$\|^없음$\|^—$\|^-$' \
  | while read p; do [ -e "$p" ] || echo "STALE: $p"; done
```
이 명령은 2026-08-27 샘플 지도로 실행 검증했다 — 실존 경로는 통과하고 없는 경로만 `STALE:`로 잡힌다.

역방향(코드엔 있으나 지도에 없는 기능)은 기계로 잡히지 않는다 → docs-organize 재실행 시 `## 미매핑`에 후보를 나열한다.

### 3. 파이프라인 배선

| 시점 | 스킬 | 하는 일 | 귀속 파일 |
|---|---|---|---|
| 스펙 | **sj-spec** | 지도를 읽고 스펙에 `## 영향 범위` 절 강제 — 의존하는 기능 + **역방향으로 나를 의존하는 기능**을 ID로 지목 | 볼트 `20_실행/플레이북/sj-spec.md` |
| 디스패치·구현 | **sj-tech-lead** | Dispatch Card에 영향 기능 ID·파일 전달. 구현 후 표의 행을 추가·갱신하고 흐름도 재생성 | 볼트 `20_실행/플레이북/sj-tech-lead.md` |
| 판정 | **sj-qa** | ① drift 검사 실행 ② **FAIL 시 판정문에 의심 기능 ID + 파일 경로 명시** | 볼트 `20_실행/플레이북/sj-qa.md` |
| 최초 생성 | **docs-organize** | 지도를 1회 생성, 재실행 시 미매핑 후보 탐지. **건강 점수 체계는 건드리지 않는다**(회귀 위험) | `skills/docs-organize/SKILL.md` |

각 역할 SKILL.md에는 산출물 계약에 경로 한 줄(`docs/FEATURE-MAP.md`)만 추가한다 — 절차는 전부 플레이북으로.

**구현 전 영향 분석은 sj-spec 단계에서 처음 생긴다.** 이것이 이 스펙의 핵심 산출이다.

### 4. 왜 볼트가 아니라 repo인가

지도의 목적은 "고장났을 때 어디를 고칠지"다. 그 문서가 코드와 다른 저장소에 살면 틀릴 확률이 시간에 비례해 올라가고, **틀린 지도는 탐색보다 나쁘다**. repo에 두면 코드와 같은 PR에서 함께 바뀌고, drift가 diff로 드러나며, `git blame`으로 기능 변경 이력을 추적할 수 있다. 분업은 이렇게 정리된다 — **repo는 "지금 뭐가 뭘 부르나"(사실), 볼트는 "왜 그렇게 설계했나"(경험·ADR).**

### 5. 자기개선 게이트 귀속

`self-harness.md`의 "변경은 파일 하나에 귀속" 원칙에 따라 제안을 5건으로 분해해 볼트 `40_프로젝트/S-skills/하네스-제안-원장.md`에 각각 5필드로 기록한다: ① 컨벤션 신설 ② sj-spec 플레이북 ③ sj-tech-lead 플레이북 ④ sj-qa 플레이북 ⑤ docs-organize SKILL.md.

## 불변식 (바뀌지 않는 것)

- **지도 불일치는 FAIL이 아니라 경고(LOW).** `reviewer-diversity.md`의 심각도 보정 — FAIL은 실제 결함에만. 낡은 문서로 배포를 막으면 사람들이 지도를 우회하기 시작하고, 그 순간 지도는 죽는다.
- **비차단 폴백.** 지도가 없는 프로젝트에서 어떤 스킬도 멈추지 않는다. `미수행: FEATURE-MAP 없음` 한 줄을 남기고 진행한다 (`honest-report.md`, 볼트 부재 폴백과 같은 패턴).
- **Judge 독립성 유지.** sj-qa는 지도를 *판정 근거*로 삼지 않는다 — 지도는 **검증 대상**(실제와 일치하는가)이자 FAIL 시 **위치 지목 도구**일 뿐이다. 판정 근거는 여전히 pm-brief + 직접 탐색.
- **사람 게이트 불변.** 이 스펙의 채택도 PR 머지·배포도 사람이 승인한다.

## 트레이드오프 (승인됨)

- **단일 파일로 시작.** 기능이 많아지면 파일이 비대해진다. OpenSpec형 `docs/features/{기능}.md` 폴더로의 승격은 **실제로 넘칠 때** 한다 — `minimal-code.md`의 게으름 사다리.
- **의존 칸은 사람·AI가 서술한다.** 정적 분석으로 import 그래프를 뽑지 않는다. 정확도는 낮지만 비용이 0이고, 기계가 못 보는 의미적 의존(같은 테이블을 쓰는 두 기능)을 담을 수 있다.
- **역방향 의존은 저장하지 않고 계산한다.** 양방향 저장은 두 배의 drift를 만든다.
- **새 스크립트 0개.** drift 검사는 bash 한 줄. 대상 프로젝트마다 스크립트를 설치하지 않는다.
