# 서술식 완료 보고 (Literate Report)

**규칙: 코드 변경을 사람에게 보고할 때(완료 보고·PR 본문)는 diff·파일 나열이 아니라 가르치는 순서로 쓴다 — ① 배경 → ② 의도 → ③ 읽기 순서 → ④ 세부.**

## 왜

하네스의 최종 게이트는 전부 사람이다(PR 머지·배포 — [human-gate.md](human-gate.md)).
**이해 없는 사람 게이트는 고무도장이다.** 구현자 관점의 집계(dev-summary)나 파일명 순
diff는 에이전트의 작업 기록이지, 사람이 변경을 이해하도록 가르치는 문서가 아니다.
이해를 생략한 승인이 쌓이면 인지 부채가 된다 — 코드가 왜 이 구조인지, 다음 요구사항을
어디에 붙일지 판단할 수 없게 된다. (Geoffrey Litt "Understanding is the new bottleneck"의
literate diff 차용 — 원시 diff가 재료 더미라면, 서술식 보고는 변경을 이야기로 편집한 것.)

## 커널 (인라인 허용)

> 완료 보고·PR 본문 순서: **배경(변경 전 동작 2~4줄) → 의도(한 문장) → 읽기 순서(파일명 순 금지, 이해 순서로) → 세부(파일 목록·diff·계약)**.

## 형식

```markdown
## 배경
{변경 전 이 영역이 어떻게 동작했는지 2~4줄 — 이 부분을 처음 보는 사람 기준}

## 의도
{이번 변경이 무엇을 바꾸는지 한 문장}

## 읽기 순서
1. `{파일}` — {왜 이 파일부터 보는지 / 전체에서 맡는 역할}
2. `{파일}` — ...

## 세부
{변경 파일 목록, API 계약, 리뷰 결과, diff 위치 등 — 위를 읽은 뒤에만 의미 있는 것들}
```

## 비대화 가드

- 배경 + 의도는 합쳐 **6줄 이내**. 사용자가 이미 아는 컨텍스트(방금 대화한 내용)는 반복하지 않는다.
- 읽기 순서는 **핵심 파일만** (전체 나열은 세부의 몫). 3~7개가 적정.
- 서술이 원시 diff를 대체하지 않는다 — 세부에서 원본(dev-summary, diff)으로 항상 연결한다.
