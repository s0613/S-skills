# sj-jev — 판단을 문장이 아니라 타입으로 받는다

에이전트에서 가장 잘 깨지는 곳은 모델이 **문장으로 답하고 코드가 그걸 파싱하는 지점**이다.
"JSON으로만 답해" → 마크다운 펜스 → 정규식 → 재시도 → 프롬프트 한 줄 추가. 이 사다리 전체가
Jev에서는 **없는 문제**다. 질문에 타입이 있고, 답이 그 타입 안으로만 돌아오고,
얼마나 확신하는지가 숫자로 같이 온다.

**Jev** = TypeSafe의 System One 모델. 텍스트를 생성하지 않고 `state`에 대한 판단을 낸다.
[docs.typesafe.ai](https://docs.typesafe.ai) · 엔드포인트 `POST https://api.typesafe.ai/v1/systemone`

> 이 스킬은 Jev를 **에이전트 안 어디에 놓을지**를 정하고 배선한다.
> API 계약의 정본은 라이브 문서다 — 이 파일이 아니다.

## Step 0. 문서와 키 (건너뛰지 않는다)

**0-1. 공식 벤더 스킬이 있으면 그쪽이 계약 정본이다.**

```bash
ls ~/.claude/plugins/cache/typesafe-ai 2>/dev/null; ls .claude/skills/typesafe-ai 2>/dev/null
```

있으면 `Skill("typesafe:typesafe-ai")`를 먼저 로드하고 이 파일은 **배선·게이트**만 담당한다.
없어도 비차단 — 아래 설치 명령을 한 번 제시하고 라이브 문서 직독으로 진행한다.

```bash
claude plugin marketplace add typesafe-ai/skills && claude plugin install typesafe@typesafe-ai
```

**0-2. 통합 코드를 쓰기 전에 해당 문서를 읽는다.** 이건 예의가 아니라 회귀 방지다 —
벤더 문서가 직접 경고하는 실패가 *"에이전트가 요청·응답 필드를 지어낸다"* 이고,
그 원인은 낡은 기억이다. 최소한:

| 쓰려는 것 | 먼저 읽을 페이지 (`.md` 붙이면 마크다운으로 온다) |
|---|---|
| 목차·쿡북 탐색 | `https://docs.typesafe.ai/llms.txt` |
| HTTP 요청/응답 계약 | `https://docs.typesafe.ai/api.md` |
| 프리미티브 세부 | `https://docs.typesafe.ai/primitives/{choice,score,noul}.md` |
| 모델·한도·가격 | `https://docs.typesafe.ai/models.md` |
| 임계값 설계 | `https://docs.typesafe.ai/confidence.md` |
| 비슷한 문제의 완성형 | `https://docs.typesafe.ai/cookbooks/…` (llms.txt에 18종) |

읽지 못했으면([정직 산출 계약](../_conventions/honest-report.md)) `미수행: 라이브 문서 접근 불가`를
기록하고, **버전 의존적인 필드명을 지어내지 않는다.** 설치된 SDK 타입을 읽는 쪽이 기억보다 낫다.

**0-3. 키는 사람 게이트다.** [console.typesafe.ai/keys](https://console.typesafe.ai/keys)에서
사용자가 직접 발급해 `TYPESAFE_API_KEY`로 export 한다. **대화에 키를 받아 적어 실행하지 않는다**
— 전사 로그에 남는다([사람 게이트](../_conventions/human-gate.md)). 웹 앱이면 키는 서버 사이드에만 둔다.

## Step 1. 이 자리가 Jev 자리인가

라우팅의 갈림길은 **답의 모양**이다. 세 갈래고, 섞으면 비싸진다.

| 필요한 것 | 간다 | 이유 |
|---|---|---|
| 알려진 규칙·계산·정확 조회·실행 | **그냥 코드** | 판단이 아니다. Jev를 끼우면 느려지고 틀릴 여지만 생긴다 |
| 의미 이해가 필요한 **좁은 판단** — 분류·라우팅·정도·참거짓·후보 중 고르기·검증 | **Jev** | 타입 있는 답 + 확률. 파싱·재시도·스키마 강제가 통째로 사라진다 |
| 문장·코드·계획을 **생성**하거나 여러 단계 추론 | **LLM(Claude/GPT)** | Jev는 텍스트를 만들지 않는다 |

**Jev로 바꿀 만한 자리를 찾는 질문:** "여기서 LLM에게 시키는 게 결국 *고르는 일*인가?"
그렇다면 생성 모델은 과잉이다. 대표적으로:

- 에이전트 **의도 라우팅** — 어느 핸들러로 보낼지 + 그 핸들러의 타입 인자
- **툴 선택** — 후보 툴을 코드가 뽑고, 의도에 맞는 것을 고르기
- **가드레일** — 입력이 정책 위반인지, 출력이 근거와 맞는지
- **리랭킹** — 검색 후보의 질의 적합도 비교
- **추출 검증** — 코드가 찾은 후보 값 중 의도한 것 선택 (생성이 아니라 **선택**이라 환각이 구조적으로 불가)
- **에스컬레이션 판단** — confidence 낮으면 사람/추론 모델로

> "생성 대신 선택." 값을 코드가 찾아 후보로 주고 Jev가 고르면, 없는 값을 지어낼 경로가 없다.
> 단 **후보에 없는 값은 고를 수 없다** — 후보 커버리지를 먼저 확인한다.

## Step 1.5. 붙이면 실제로 나아지나 (기본값은 "안 붙인다")

Step 1은 **모양이 맞는지**만 봤다. 모양이 맞아도 효과가 없는 자리가 있고,
그 자리에 붙이면 의존성과 키 관리와 네트워크 실패 경로만 늘어난다.
[최소 코드 사다리](../_conventions/minimal-code.md) — 안 써도 되는 길을 먼저 따진다.

**이 단계의 산출은 판정이다: `붙인다` / `측정 후 결정` / `안 붙인다` + 근거 한 줄.**
근거 없이 "붙이면 좋아집니다"라고 쓰지 않는다.

### 효과가 나는 자리의 신호 (2개 이상이면 `붙인다`)

- 파싱·재시도·스키마 강제 코드가 **실제로 있고**, 깨진 적이 있다 (그 커밋·이슈를 가리킬 수 있다)
- 이 판단이 **반복 호출된다** — 요청마다, 문서마다, 후보마다. 단가 차이가 곱해진다
- **"모르겠다"를 표현할 자리가 필요하다** — 지금은 확신 없이도 무조건 한 갈래로 간다
- 분기·라벨 집합이 **고정**돼 있다 (Choice/Score로 그대로 떨어진다)
- 지금 이 자리에서 쓰는 생성 모델 콜이 **없어지거나 작아진다**

### 효과가 없는 자리의 신호 (하나라도 걸리면 `안 붙인다`)

- **LLM 콜이 사라지지 않고 Jev 콜이 추가된다** — 가장 흔한 헛스윙. 순증이면
  지연도 비용도 올라간다. *대체*인지 *추가*인지를 먼저 답한다
- 지금 코드가 이미 결정론적으로 처리하고 **틀린 적이 없다** — 고칠 게 없다
- 호출이 드물다 (배포당 한 번, 사람이 수동 실행) — 단가 개선이 곱해지지 않는다
- 산출물이 **문장·코드·계획**이다 — Jev는 만들지 못한다
- 어차피 사람이 전수 검토한다 — 자동 판단의 값이 사라진다
- 선택지가 열려 있다(자유 텍스트 값) — 후보를 코드가 못 좁히면 고를 게 없다

### `측정 후 결정`이면 이렇게 잰다

판정이 갈리면 추측으로 메우지 않는다. **골든셋 20~50건**을 만들고
현재 방식과 Jev를 같은 입력으로 돌려 세 가지를 나란히 놓는다.

| 재는 것 | 왜 |
|---|---|
| 정확도 (골든셋 대비) | 나아지지 않으면 나머지는 볼 필요가 없다 |
| p50·p95 지연 | 콜 순증이면 여기서 드러난다 |
| 요청당 비용 | Jev는 입력 토큰만 과금이지만 **실측한다** — 가격·한도는 `models.md` |

여기에 하나 더: **에스컬레이션 비율**. confidence 임계값을 걸었을 때 사람에게
넘어가는 비율이 운영 가능한 수준인가. 30%가 사람에게 가면 자동화가 아니다.

`TYPESAFE_API_KEY`가 없어 실측하지 못했으면
`미수행: 실호출 미검증 — 효과 판정은 추정` 으로 남긴다.
[정직 산출 계약](../_conventions/honest-report.md) — 재보지 않은 개선을 개선이라 쓰지 않는다.

## Step 2. 프리미티브 고르기

| 답이 | 타입 | 돌아오는 것 | 틀리기 쉬운 지점 |
|---|---|---|---|
| 정해진 집합 중 하나 (순서 없음) | **Choice** | `choice`, `probabilities`, `confidence` | 아무것도 안 맞을 수 있으면 `other`/`none` 옵션을 넣는다. 옵션 최대 255 |
| 서술된 축 위의 정도 | **Score** | `score`(레벨 사이 값 가능), `legend`, `probabilities`, `confidence` | 레벨은 **구체적 상황**으로 쓴다. "보통"은 레벨이 아니다. 2~10개 |
| 조건이 참인가 | **Noul** | `noul` (0~1) | **별도 confidence 없다.** 0.5는 "중간 정도"가 아니라 "예/아니오 반반" |

**Noul 0.5 함정이 실무 1순위 오답이다.** "파이썬 잘하나?"를 Noul로 물으면 0.5가
*중급*인지 *모르겠다*인지 구분되지 않는다. 정도를 재려면 Score, 예/아니오면
조건을 명확히 정의한다("이력서에 업무에서 파이썬을 썼다고 적혀 있는가").

**둘 다 맞아 보이면, 코드가 바로 분기할 수 있는 쪽을 고른다.** Choice는 `if/elif`,
Score는 임계값, Noul은 `if`에 그대로 얹힌다.

여러 라벨이 **동시에** 참일 수 있으면 Choice 하나가 아니라 **라벨당 Noul 하나**다.

## Step 3. state와 질문 쓰기

**state = 판단에 필요한 사실 전부.** 문자열도 되고 JSON 객체·배열도 된다. 여러 조각이면
이름 있는 필드로 준다. 질문에서는 백틱 경로로 가리킨다 — `` `ticket.messages[0].text` ``.

**질문 = `instructions`(무엇을 판단할지) + `criteria`(가능한 답).**
질문 ID는 **모델에 전달되지 않는다** — ID가 아무리 설명적이어도 의미는 `instructions`에 다 쓴다.

**한 질문에 한 판단.** 여러 요인에 걸친 판단은 요인별로 쪼개고 **가중치는 코드에**
둔다. 우선순위가 바뀌면 프롬프트를 고쳐 쓰는 게 아니라 상수를 바꾼다.

### 한 요청에 몰아 넣는다 (이 스킬의 핵심 계약)

같은 state에 대한 질문은 **전부 한 요청에**. 병렬 평가라 질문을 더해도 응답 시간이 거의
안 늘고, 입력 토큰만 조금 더 든다. **어떤 입력에서만 쓸 질문(speculative)도 미리 물어 두고
코드가 필요한 답만 쓴다** — 문서 기준 13질문 배치가 13콜 대비 훨씬 싸고 빠르다.

> 코딩 에이전트는 사람보다 "한 콜에 한 질문" 습관에 잘 빠진다. 벤더 문서가 이걸 명시적으로
> 경고한다. **질문을 나눠 부르고 있으면 그건 설계가 아니라 습관이다.**

**두 번째 요청은 예외다.** 첫 답이 있어야 (a) 새 증거를 가져오거나 (b) state를 새로 만들거나
(c) 다음 질문의 선택지가 정해질 때만 나눈다. 그 외에는 같이 묻고 코드가 버린다.

**한도는 확인하고 쓴다** — 요청 전체와 `state`+최장 질문에 각각 토큰 예산이 있다
(`models.md`). 긴 state를 fan-out으로 채울 때 먼저 걸린다.

## Step 4. confidence를 행동 게이트로

Choice·Score 답에는 `confidence`(0~1)가 확률 분포에서 파생돼 같이 온다. 이게 에이전트에
**"모르겠다"를 표현할 자리**를 준다 — 그게 없는 시스템은 신뢰할 수 없다.

3구간이 출발점이고, **임계값은 결과의 위험도에 따라 다르게 잡는다.**

```
낮음  → 행동하지 않는다. 사람·추론 모델·폴백으로
중간  → 확인받고 진행 (사용자 확인·리뷰 플래그·증거 추가)
높음  → 자동 실행
```

같은 시스템 안에서도 **읽기 동작과 파괴적 동작의 문턱은 다르다.** 잔액 조회 0.5,
이체 승인 0.9처럼. 임계값은 **사용자 데이터로 검증하고 나서** 굳힌다 —
쿡북 숫자는 예시지 상수가 아니다.

**confidence를 남용하지 않는 규칙 셋:**

1. **그냥 최선을 고르는 게 목적이면 임계값이 필요 없다.** 최고 확률 옵션을 쓰면 된다.
2. **쓰지 않을 분기의 불확실성은 무시한다.** speculative 질문이 흔들려도 상관없다.
3. **confidence는 분포가 뾰족한 정도지, 워크플로가 옳다는 보증이 아니다.** 타입은 인터페이스를
   보장하지 진실을 보장하지 않는다. 대안이 여러 개 다 괜찮아서 낮게 나오는 경우도 있다.

## Step 5. 에이전트 어디에 배선하나

[sj-agent-dev](../sj-agent-dev/SKILL.md)의 10축 중 Jev가 실제로 들어가는 자리는 정해져 있다.
전부에 끼우는 게 아니다.

| 축 | Jev의 자리 | 형태 |
|---|---|---|
| **오케스트레이션** | 의도·핸들러 라우팅 | Choice(핸들러) + 분기별 인자 질문을 같은 콜에 speculative로 |
| **도구 계층화** | 툴 선택·인자 채우기 | 후보를 코드가 좁히고 Choice로 선택. 실행은 코드 |
| **가드레일** | 입력 정책 위반·출력 근거 일치 | 정책 조항당 Noul. "중대 위반 하나라도"는 가중합이 아니라 개별 조건 |
| **컨텍스트 관리** | 검색 후보 리랭킹·관련성 판정 | 후보별 Score 또는 Choice. 상위 N만 LLM 컨텍스트로 |
| **평가·자기반성** | 출력 검증·인용 확인 | Noul(주장↔근거 일치) → 낮으면 에스컬레이션 |
| **런타임 루프** | 다음 단계 선택 | Choice(다음 행동). 목표·관측은 코드가 보관 |
| 역할 분리 / 옵저버빌리티 / 메모리 계층 / 그래프 토폴로지 | **직접 자리 없음** | 구조·저장·계측은 코드 영역 |

**코드가 워크플로를 소유한다.** Jev는 "프로그래밍 가능한 상식"을 공급할 뿐,
상태 보관·실행·재시도·기록은 전부 코드다. 추론된 판단과 관측된 사실을 **섞어 저장하지 않는다**
— 상태가 바뀌었는데 오래된 판단을 적용하는 것이 에이전트에서 가장 조용한 버그다.

---

## Step 6. 사람이 리뷰할 수 있게 남긴다

Jev 코드에서 사람이 실제로 검토해야 하는 건 **질문 문구와 임계값 상수** 둘뿐이다.
여기저기 흩어 놓으면 리뷰가 불가능해진다.

**질문과 임계값을 파일 하나에 모은다.** (`typesafe_questions.py` / `judgments.ts` 등)
호출부는 그 상수를 참조만 한다. 에이전트는 질문 문구를 잘 못 쓰는 편이라,
사용자와 **같이 고치는 것을 전제**로 한 곳에 둔다.

**테스트는 대표 케이스로 한다.** 실패하면 분리해서 본다 — 증거 누락인가, 모델 판단 오류인가,
코드 오류인가, 서비스 장애(429/529)인가. 넷은 고치는 곳이 다르다.
429·529는 지수 백오프 재시도이고, 공식 SDK는 기본 정책에 이미 들어 있다.

응답의 `model` 필드에 실제로 답한 버전이 실려 온다 — **임계값을 튜닝했으면 별칭(`jev-latest`)이
아니라 그 버전 ID를 고정**하고 이동 시점을 직접 고른다. 별칭은 소리 없이 움직인다.

## 실행 경로

| 사용자가 원하는 것 | 이 스킬이 하는 일 |
|---|---|
| "이 프로젝트에 Jev 쓸 데 찾아줘" | 프롬프트+파싱·취약한 분류 분기를 훑어 후보를 뽑고, **후보마다 Step 1.5 판정을 붙여** 제시한다. 전부 "붙이자"가 나오면 판정을 안 한 것이다 |
| "이 분기를 Jev로 바꿔줘" | Step 1.5 먼저 — `안 붙인다`가 나오면 **그렇게 말하고 멈춘다**. 그다음 Step 0 문서 읽기 → 프리미티브 선택 → 상수 파일 + 호출부 → 대표 케이스 실행 |
| "새로 만들어줘" | 원하는 최종 동작에서 거꾸로 필요한 판단을 도출. 규칙·계산은 코드로 남긴다 |
| "실험해 보고 정해줘" | `TYPESAFE_API_KEY`가 있으면 실제 호출로 질문·임계값을 조정. 결과를 근거로 제안 |

키가 없는 상태에서 **호출했다고 보고하지 않는다.** 코드만 쓰고
`미수행: TYPESAFE_API_KEY 없음 — 실호출 검증 안 함`으로 남긴다.

[최소 코드 사다리](../_conventions/minimal-code.md)가 여기도 적용된다 —
래퍼 클래스·추상 레이어를 먼저 만들지 않는다. 공식 SDK(`typesafe-sdk` / `@typesafe-ai/sdk`)
호출 한 줄과 상수 파일이면 대개 끝이다.

## 흔한 실수

- **모양이 맞으면 무조건 붙인다** → 적합성은 효과가 아니다. Step 1.5 판정 없이 전환을 제안하지 않는다
- **LLM 콜을 그대로 두고 Jev를 추가한다** → 순증이라 느려지고 비싸진다. *대체*인지 *추가*인지가 먼저
- **재보지 않은 개선을 개선이라 쓴다** → 골든셋 없이 "더 정확해집니다"는 추정이다. `미수행:`으로 남긴다
- **요청·응답 필드를 기억으로 쓴다** → 벤더가 명시한 1순위 실패. Step 0에서 `api.md`를 읽는다
- **질문을 콜마다 하나씩 부른다** → 느리고 비싸다. 같은 state면 전부 한 요청에
- **Noul로 정도를 잰다** → 0.5가 "중간"인지 "모름"인지 사라진다. 정도는 Score
- **임계값을 쿡북에서 베껴 굳힌다** → 예시일 뿐. 자기 데이터로 검증하고 위험도별로 나눈다
- **읽기 동작과 파괴적 동작에 같은 문턱** → 잘못된 조회는 되돌려지고 잘못된 이체는 안 된다
- **confidence를 정답률로 읽는다** → 분포가 뾰족한 정도다. 타입은 인터페이스 보장, 진실 보장 아님
- **생성 모델로 충분한 자리를 Jev로 바꾼다** → 문장·코드 생성은 Jev가 못 한다. 판단만 넘긴다
- **후보를 좁히지 않고 "고르게" 한다** → 후보에 없으면 못 고른다. 커버리지가 먼저
- **질문·임계값을 호출부에 흩는다** → 사람이 리뷰할 수 없다. 파일 하나로
- **API 키를 대화에 받아 실행** → 전사 로그 잔류. 프론트엔드 번들에 넣는 것도 같은 사고
