# Architecture 모드 — 깊게 만들 후보 찾기

얕은 모듈을 깊게 만들 **후보를 찾아 보여 주고**, 사용자가 고른 하나를 질문 라운드로 설계 결정까지 끌고 간다.
목표는 테스트하기 쉽고 에이전트가 찾아가기 쉬운 코드베이스다.

**이 모드는 코드를 고치지 않는다.** 진단이지 구조 구출이 아니다 — 오래된 코드베이스에서 진짜 후보는 찾지만
엉킨 것을 대신 풀어 주지는 않는다. 구현은 결정이 끝난 뒤 sj-spec → sj-tech-lead로 넘긴다.
며칠에 한 번 돌리는 용도다.

> [mattpocock/skills](https://github.com/mattpocock/skills) `improve-codebase-architecture` (Matt Pocock, MIT) 차용.

**어휘:** [deep-modules](../_conventions/deep-modules.md)의 단어를 그대로 쓴다 — 모듈·인터페이스·깊이·이음매·어댑터·
레버리지·국소성. "컴포넌트·서비스·API·경계"로 흐르지 않는다. 도메인 이름은 `GLOSSARY.md` 단어로 부른다
("FooBarHandler"가 아니라 "주문 접수 모듈") — [glossary](../_conventions/glossary.md).

## Step 1. 범위부터 (YAGNI)

깊게 만드는 이득은 *앞으로의 변경*이 쉬워지는 것이라 **최근 자주 바뀐 곳**에 가중치를 둔다.

- 사용자가 방향(모듈·하위 시스템·아픈 곳)을 줬으면 그대로 간다.
- 아니면 핫스팟을 뽑는다:

```bash
git log --since="90 days ago" --name-only --pretty=format: \
  | grep -vE '^$|^(docs|node_modules|dist)/|lock' | sort | uniq -c | sort -rn | head -20
```

- 변경이 흩어져 핫스팟이 없으면 범위를 넓힌다.
- 범위 안의 `GLOSSARY.md`(또는 `GLOSSARY-MAP.md`)와 `docs/adr/`를 먼저 읽는다 — ADR에 적힌 결정은 다시 논쟁하지 않는다.

## Step 2. 탐색

범위를 지정해 **Explore 서브에이전트**에 맡긴다. 정해진 휴리스틱을 돌리지 말고 걸리는 곳을 적게 한다:

- 개념 하나를 이해하려고 작은 모듈 여러 개를 오가야 하는 곳은?
- 인터페이스가 구현만큼 복잡한 **얕은** 모듈은?
- 테스트하려고 순수 함수를 뽑았는데 진짜 버그는 그 함수를 *부르는 방식*에 숨은 곳은? (국소성 없음)
- 강하게 묶인 모듈이 이음매를 넘어 새는 곳은?
- 테스트가 없거나, 지금 인터페이스로는 테스트하기 어려운 곳은?

얕다고 의심되는 것마다 **삭제 테스트**를 한다: 지우면 복잡성이 한곳에 모이나(신호), 그냥 옮겨 가나?
의존성 종류(프로세스 안·로컬 대체 가능·원격이지만 우리 것·진짜 외부)를 분류해 두면 Step 4의 테스트 방법이 정해진다.

## Step 3. HTML 보고서

`${TMPDIR:-/tmp}/architecture-review-$(date +%Y%m%d-%H%M%S).html`에 자립형 HTML 하나를 쓴다 — **repo에 남기지 않는다.**
`open {경로}`로 열고 절대 경로를 알려 준다.

후보마다 카드 하나:

| 칸 | 내용 |
|----|------|
| 파일 | 관련 파일·모듈 |
| 문제 | 지금 구조가 왜 마찰을 만드나 |
| 해결 | 무엇이 바뀌나 — 평이한 말로 |
| 이득 | 국소성·레버리지로, 그리고 테스트가 어떻게 나아지나 |
| 전·후 그림 | 나란히. 전: 작은 상자 여러 개와 오가는 화살표 / 후: 작은 인터페이스 아래 큰 상자 하나 |
| 추천 강도 | `Strong` · `Worth exploring` · `Speculative` 배지 |

- 그림은 손으로 그린 HTML/CSS·인라인 SVG로 그린다. 즉석 mermaid는 쓰지 않는다 ([report-diagram](../_conventions/report-diagram.md)).
  볼트 취향 프로필이 있으면 그 금지 규칙(굵은 좌측 테두리 등)을 지킨다.
- **ADR과 충돌하는 후보**는 마찰이 ADR을 다시 열 만큼 클 때만 싣고, 카드에 "ADR-0007과 충돌 — 그래도 다시 볼 이유: …"를 단다.
  ADR이 막는 이론상 리팩터링을 줄줄이 나열하지 않는다.
- 마지막에 **가장 먼저 할 것** 하나와 이유.
- **아직 인터페이스를 제안하지 않는다.** 보고서를 연 뒤 "어느 후보를 더 파 볼까요?"라고만 묻는다.

## Step 4. 질문 라운드

사용자가 후보를 고르면 [grilling](../_conventions/grilling.md)으로 결정 트리를 걷는다 — 제약, 의존성,
깊어진 모듈의 모양, 이음매 뒤에 둘 것, 살아남을 테스트(겹치지 말고 바꾼다).

결정이 굳는 그 자리에서:

- 깊어진 모듈의 이름이 용어집에 없는 개념이면 `GLOSSARY.md`에 추가한다(없으면 이때 만든다).
- 흐린 말이 정리되면 바로 용어집을 고친다.
- 사용자가 **무게 있는 이유로 후보를 기각**하면 "다음 점검이 다시 제안하지 않게 ADR로 남길까요?"라고 제안한다.
  일시적인 이유("지금은 할 때가 아님")나 자명한 이유면 제안하지 않는다.
- 다른 인터페이스를 비교하고 싶으면 서브에이전트 2~3개에 **서로 크게 다른** 인터페이스를 따로 설계시키고
  깊이·국소성·이음매 위치로 나란히 비교한다.

## Step 5. 인계

프론티어가 비면 결정 요약을 5줄 이내로 쓰고 다음을 제안한다:

```
다음: /spec {후보 이름} 깊게 만들기   ← 스펙이 이 결정을 받아 Tech Lead로 넘긴다
```

**비대화형 실행:** Step 3까지만 하고 Step 4는 하지 않는다. 보고서 경로와 가장 먼저 할 것 하나만 보고한다
([noninteractive](../_conventions/noninteractive.md)).
