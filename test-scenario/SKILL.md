# test-scenario

기능별 테스트 프롬프트 생성 → Chrome 확장 실행 → 결과 비교 → 개선 방향 도출.

실행은 Claude Chrome 확장에서 유저가 직접 한다. 이 스킬은 **프롬프트 생성**과 **결과 분석**에 집중한다.

---

## 모드 감지

실행 시 아래 순서로 모드를 자동 판단한다.

1. `docs/test-scenarios/scenarios/`에 파일이 없으면 → **generate 모드**
2. 유저 메시지에 테스트 결과처럼 보이는 내용(PASS/FAIL/판정 등)이 포함되어 있으면 → **report 모드**
3. 그 외 → AskUserQuestion으로 모드 선택

```
A) 시나리오 생성 — 기능 분석 후 테스트 프롬프트 작성
B) 결과 보고서 저장 — 실행 결과를 붙여넣어 비교 분석
C) 개선 현황 — 지금까지 누적된 pass/fail 추이 보기
```

## Generate 모드

### Step 1: 기능 목록 수집

다음 순서로 테스트할 기능 목록을 만든다.

1. `docs/prd.md` — Features 섹션에서 기능 목록 추출
2. `docs/STATUS.md` — Features 테이블에서 추출
3. 위 둘이 없으면 코드에서 직접 추론:
   - 라우트 파일 (routes/, pages/, app/)
   - API 엔드포인트 (controllers/, handlers/, api/)
   - 주요 컴포넌트 (components/, screens/, views/)

기능 목록을 유저에게 보여주고 확인을 받는다:

```
발견된 기능 목록:
1. 회원가입
2. 로그인 / 로그아웃
3. 프로필 수정
...

테스트에서 제외할 기능이 있으면 말씀해주세요. 없으면 진행합니다.
```

AskUserQuestion으로 확인 후 진행. 유저가 제외 기능을 말하면 목록에서 제거.

### Step 2: 기능별 시나리오 프롬프트 작성

각 기능마다 `docs/test-scenarios/scenarios/YYYY-MM-DD-{feature-slug}.md` 파일을 생성한다.

**파일 포맷:**

```markdown
# 테스트 시나리오: {기능명}

**생성일:** YYYY-MM-DD
**버전:** 1.0
**상태:** 미실행

---

## 목적
{이 테스트가 검증하는 것 — 1-2문장}

## 사전 조건
- URL: {테스트 시작 URL — 코드에서 추론하거나 "확인 필요"로 표시}
- 인증 상태: {로그인 필요 여부}
- 필요한 데이터: {테스트 전 준비해야 할 데이터}

---

## 테스트 단계

### Step 1: {동작 설명}
**실행:** {구체적인 행동 — 클릭, 입력, 이동 등}
**입력값 (있는 경우):** {테스트 데이터}
**기대 결과:** {이 단계에서 나와야 하는 결과}
**실패 조건:** {이것이 나오면 실패}

### Step 2: {동작 설명}
...

---

## 엣지 케이스

| 케이스 | 입력 | 기대 결과 |
|--------|------|-----------|
| {비정상 입력} | {값} | {에러 메시지 또는 처리 방식} |
| {빈 값} | {값} | {기대 결과} |

---

## 종합 판정 기준

**PASS 조건:**
- {측정 가능한 성공 기준 1}
- {측정 가능한 성공 기준 2}

**FAIL 조건:**
- {이것 중 하나라도 발생하면 실패}

**PARTIAL 조건:**
- {핵심 기능은 동작하지만 일부 문제 있는 경우}
```

### Step 3: 시나리오 인덱스 생성

`docs/test-scenarios/README.md`에 전체 현황 테이블을 생성한다.

```markdown

**마지막 업데이트:** YYYY-MM-DD
```

### Step 4: 완료 보고

## Report 모드

유저가 `[결과] ... [/결과]` 형식의 텍스트를 붙여넣으면 진입한다.

### Step 1: 결과 파싱

유저 메시지에서 결과 블록을 파싱한다:
- 기능명
- 판정 (PASS / FAIL / PARTIAL)
- 단계별 통과 여부
- 실제 결과 내용
- 메모

여러 기능의 결과가 한 번에 들어올 수 있다. 모두 처리한다.

### Step 2: 기대 결과와 비교

해당 기능의 시나리오 파일(`docs/test-scenarios/scenarios/`)을 읽어 기대 결과와 실제 결과를 비교한다.

각 단계별로:
- ✅ 통과: 기대 결과와 일치
- ❌ 실패: 기대 결과와 불일치 — 구체적으로 무엇이 달랐는지 기록
- ⚠️ 부분: 핵심은 동작하지만 세부 차이 있음

### Step 3: 보고서 저장

`docs/test-scenarios/reports/YYYY-MM-DD-{feature-slug}-report.md` 생성:

```markdown
# 테스트 결과 보고서: {기능명}

**실행일:** YYYY-MM-DD
**시나리오 버전:** {버전}
**판정:** PASS / FAIL / PARTIAL

---

## 단계별 결과

| 단계 | 기대 결과 | 실제 결과 | 판정 |
|------|-----------|-----------|------|
| Step 1 | {기대} | {실제} | ✅/❌/⚠️ |
| Step 2 | {기대} | {실제} | ✅/❌/⚠️ |

## 엣지 케이스 결과

| 케이스 | 기대 결과 | 실제 결과 | 판정 |
|--------|-----------|-----------|------|

## 실패 분석

{FAIL 또는 PARTIAL인 경우만 작성}

### 실패 원인 추정
{코드/시나리오를 보고 가능한 원인 추론}

### 재현 조건
{이 실패를 재현하는 최소 조건}

## 메모
{유저가 입력한 추가 관찰사항}
```

### Step 4: 개선 방향 도출

실패한 항목에 대해 `docs/test-scenarios/improvement/YYYY-MM-DD-improvement.md`에 추가 또는 업데이트:

```markdown
# 개선 방향

**업데이트:** YYYY-MM-DD

## 미결 항목 (Fix 필요)

| 기능 | 실패 단계 | 추정 원인 | 우선순위 | 첫 발견 |
|------|-----------|-----------|----------|---------|
| {기능} | {단계} | {원인} | P1/P2/P3 | YYYY-MM-DD |

## 개선 제안

### {기능명} — {실패 단계}
**증상:** {무엇이 잘못됨}
**추정 원인:** {코드 분석 기반 원인}
**제안 수정:** {구체적인 수정 방향 또는 코드 위치}
**검증 방법:** {수정 후 이 시나리오를 다시 실행해서 확인}

## 해결된 항목

| 기능 | 해결일 | 내용 |
|------|--------|------|
```

### Step 5: 인덱스 업데이트

`docs/test-scenarios/README.md`의 해당 기능 행을 최신 판정으로 업데이트.

### Step 6: 완료 보고

```
결과 저장 완료.

📊 이번 결과:
   PASS:    N개 기능
   PARTIAL: N개 기능
   FAIL:    N개 기능

❌ 실패 항목 (개선 필요):
   - {기능}: {실패 단계} — {추정 원인 한 줄}

📁 보고서: docs/test-scenarios/reports/
📋 개선 방향: docs/test-scenarios/improvement/

다음 단계: 개선 후 실패한 시나리오를 다시 Chrome 확장으로 실행해주세요.
```

## 시나리오 업데이트

기능이 변경되었을 때 기존 시나리오를 업데이트하려면:

```
/test-scenario update {기능명}
```

기존 시나리오 파일을 읽고, 현재 코드와 비교해 변경된 부분을 반영한다.
버전을 1.0 → 1.1로 올리고, 변경 이력을 파일 하단에 추가한다.

```markdown
---
## 변경 이력
- v1.1 (YYYY-MM-DD): {변경 내용}
- v1.0 (YYYY-MM-DD): 최초 생성
```
